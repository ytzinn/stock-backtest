## 0. 최우선 지시 (불변식)

1. **`REBALANCE_DATES`(반기 23개)를 절대 수정하지 않는다.** 이 리스트는 `engine.py`·`ablation.py`·`gate_analysis.py::_closed_dates()`·holdings tape·`export_portfolios.py`가 전부 참조한다. 여기에 분기 날짜를 추가하면 **기존 결정론 태그 전체의 구간 집합이 조용히 바뀐다.** 분기 캘린더는 `REBALANCE_DATES_Q`라는 **별도 상수 + config 파라미터**로만 도입한다.
2. **기존 결정론 태그의 완결 20구간 편입·수익률 불변.** 분기 결과는 신규 태그(`*_Q` 접미사)로만 산출한다.
3. **Look-ahead 금지.** 모든 재무 조회 `available_from <= rebalance_date`. Q1/Q3 추가로 PIT 표면적이 2배가 되므로 이 조항의 위험도도 2배다.
4. **파라미터는 소비되거나 예외를 던진다** (ghost parameter 재발 방지). `rebalance_freq`는 반드시 실제 분기 처리에 도달해야 한다.
5. **조용한 실패 금지.** 특히 §4의 "누적 vs 3개월" 오염은 예외 없이 그럴듯한 숫자를 만들어낸다 — §8 게이트로 강제 검출한다.
6. **#24 라이브 포워드(2026-08-19, SPEC_11 §5)는 반기 기준 그대로 실행한다.** 본 SPEC의 어떤 결과도 #24 manifest를 바꾸지 않는다.

### DEBT-2. TTM 연도 위치 정렬 `[검증된 코드 사실]` — §4의 핵심

`backtest/data_access.py::load_pit_series`는 연도 키를 버리고 `[현재, t-1, t-2]` **위치 리스트**로 반환한다(`sorted_years = sorted(...)[:n_years]`). `load_pit_series_ttm`의 `_make_ttm(fyp, h1c, h1p)`은 이 리스트 위치가 연속 연도라고 가정한다. **중간 연도가 하나 빠지면 `FY_2021 − H1_2020 + H1_2022` 같은 조합이 예외 없이 만들어진다.** Q1/Q3는 결측 확률이 높아 위험이 확대된다(§4-2).

**처리 (외부 계약 보존)**: **내부 로더만** 연도 키 dict로 바꾼다.
```
load_pit_by_year()     → 내부용 {ticker: {year: accounts}}  (신규)
load_pit_series_ttm()  → 외부용 {ticker: [current, previous, previous2]}  (계약 유지)
```
현재 필터들이 `[현재, t-1, t-2]` 위치 계약에 의존하므로 **공개 인터페이스를 바꾸면 수정 범위가 폭증한다.** 내부만 연도 키로 정확 조회하고 외부 계약은 그대로 둔다. `TTM_y = FY_{y-1} − interim_{y-1} + interim_y`를 명시적 연도 조회로 계산. 이 리팩터링도 인컴번트 H1 수치를 바꿀 수 있으므로 선행 PR로 분리하고, QG0은 이 위에서 돈다(§8).

### DEBT-3. 게이트 시점 선택 — `fiscal_year` 부재 `[검증된 코드 사실]`

`load_gate_passed_tickers`는 `DISTINCT ON (ticker) ... ORDER BY year DESC`로 **"available한 것 중 최신 연도"**를 고른다(테스트 I-5 통과). 최신 연도 선택·PIT 인지 자체는 정상이다.

**문제**: 이 로직은 "가장 최신"을 고르지 "이 앵커가 원하는 사업연도"를 고르지 않는다. 예: 2025년 5월 Q1 앵커에서 어떤 기업의 **2025 Q1이 늦게 제출**되면 **2024 Q1이 조용히 선택**된다. 룩어헤드는 아니지만 1년 묵은 분기를 최신처럼 쓰는 stale 오류다. 반기(연 2회)에서는 이 창이 짧아 덜 부각됐으나 **분기 4앵커에서 커진다.** 기존 QG0 규칙("available Q1 중 최신인지")으로는 못 잡는다.

**처리**: `RebalancePoint`에 **`fiscal_year`를 명시**(§7-3)하고, 로더가 `(ticker, fiscal_year, report_type)`을 **정확 조회**하도록 확장한다. 원하는 기간 보고서가 미공개면 **해당 앵커에서 종목 제외 + `late_or_missing_current_report`로 집계**(사전등록 정책). 이 방식은 분기 전략에 "신속 공시 기업 선호" 효과를 섞으므로 **그 사실을 판정 보고서에 명시**한다. `universe_gate_pit`의 시점 차원 부재(CORR-GATE-003, "감수")는 SPEC_13이 해결하진 않되 악화 여부를 QG0에서 검증(§8).

### DEBT-4. 거래비용 산식 — 첫 진입 매도비용 부과 `[검증된 코드 사실]`

`_calc_turnover`는 첫 구간에 `if not prev: return 1.0`이고, 엔진은 `tc = turnover × (COST_SELL + COST_BUY)`를 적용한다. **따라서 첫 진입은 팔 종목이 없는데도 매도비용 0.505%가 부과된다.**

`[Claude 의견]` 이는 캘린더 실험이 만드는 문제가 아니라 **인컴번트에도 이미 있는 특성**이다. 모든 전략의 첫 구간에 동일 적용되므로 상대 비교에서 상당 부분 상쇄되지만, warm-up 정규화(§9-2b)와 공통 시작일 처리에서 첫 진입 비용이 후보별로 다르게 잡히면 판정에 새는 지점이 된다.

**처리**: 매수/매도 회전율을 분리하고 **첫 진입에는 매수비용만** 적용, 매도는 시장·시점별 요율로 계산한다.
```python
buy_turnover  = sum(max(curr.get(t,0) - prev.get(t,0), 0) for t in tickers)
sell_turnover = sum(max(prev.get(t,0) - curr.get(t,0), 0) for t in tickers)
tc = buy_turnover*buy_cost + Σ_market sell_turnover[m]*sell_cost(m, date)
```
**이 역시 인컴번트 수치를 바꾸므로 신규 `CORR` 번호를 받아 DEBT-1과 함께(또는 그 안에서) 처리**하고 baseline을 재고정한다. TC-PRE는 요율 선택 **전에** 이 산식 수정을 포함한다.

> **`[Claude 의견]` 선행 부채 처리 순서.** DEBT-4(비용 산식 buy-only 분리) → DEBT-1(요율 확정) → DEBT-2(연도 키 로더) → DEBT-3(fiscal_year 조회)는 전부 **인컴번트 수치를 바꾸므로 각각 CORR 번호 + 단독 PR + 승인 후 baseline 갱신**이다. 전부 **Q-A 승인 후 본 실행 전**에 끝나야 하며, QG0은 그 위에서 돈다(§8).

## 1. 먼저 — 이 실험을 지금 해야 하는가 (선결 판단)

### 1-1. 분기 전환은 G5 실패의 해법이 되기 어렵다

`[검증된 사실]` 2026-07-20 게이트 판정 §3: 낙폭(−54.22%, 2018-05-31 → 2020-03-19)의 원천은 랭킹이 아니라 **유니버스 노출**이다. 같은 구간에서 랭킹 없는 `U_pbr_path_ew`가 −52.3%, KOSDAQ 지수가 −51.3%였다.

`[검증된 사실]` CONTRACT-PF-001: 종목 미달 시에도 **충족 종목 수만큼 전액 투자, 현금 없음.** 전략은 항상 100% 투자 상태다.

`[Claude 의견]` 위 둘을 결합하면 — 리밸런싱을 자주 해도 **빠져나갈 곳이 없다.** 모멘텀 필터가 더 자주 발화해 종목을 갈아탄들 자산군 노출은 그대로다. 분기 전환이 일별 MDD를 −45%보다 얕게 만들 경로는 사실상 "낙폭 국면에서 상대적으로 덜 빠지는 종목으로 더 자주 교체"뿐이고, 이는 −52%대 자산군 낙폭 앞에서 수 %p 수준의 효과다. **G5 해결을 기대하고 이 실험을 하면 안 된다.**

G5를 실제로 겨냥하는 축은 별개다(전부 사용자 결정 사항, 본 SPEC 범위 밖): 현금 비중 허용, 지수 선물 헤지, SPEC_07/08 국면 오버레이, 포지션 사이징. 07-20 보고서 §3 [Claude 의견]과 동일한 입장.

### 1-2. 그러면 분기 전환의 진짜 가설은 무엇인가

### 1-3. 사전등록 체계와의 충돌 점검 — 반드시 사용자 확인

`[검증된 사실]` SPEC_10 §5-3 FAIL 브랜치 사전등록: *"채택 보류. **그리드 재개·룰 재조합 금지**. … 어떤 경우든 결과는 보고서로 발행하고 다음 행동은 사용자 결정."*

`[Claude 의견]` 리밸런싱 주기는 필터 룰의 재조합이 아니므로 문자 그대로의 위반은 아니다. 그러나 **G5 실패 직후 새 자유도 축을 여는 것**은 "게이트가 통과할 때까지 축을 바꾸는" 전형적 패턴이며, 프로젝트가 일관되게 경계해온 gate-laundering이다. 따라서 착수 조건으로 다음을 요구한다:

- (a) 본 SPEC은 **G5 판정에 관여하지 않는다**고 명시 (SPEC_12 §5-8 상위 게이트 불간섭 조항과 동일 성격).
- (b) **주기 축은 1회 시도로 종결.** 분기 1개 후보만 검정한다. 실패 시 월별·6주·격월 등 **다른 주기 탐색 금지** (그리드화 금지).
- (c) 미탐색 축(모멘텀 조건 / 포지션 사이징 / 종목 수 / 리밸런싱 주기 / 배당) 중 하나를 소진한다는 사실을 사전등록 문서에 다중검정 고지로 기록.

**`[확정 2026-07-24]`** 자유도가 실제로 소모되는 시점은 **Q-A(DART 수집) 착수**다. 그 이전(설계·선행 부채 처리)까지는 주기 축이 소진되지 않은 상태이며, Q-A 승인은 별도로 받는다(§3 로드맵).

### 1-4. 안 C 편입 — **확정 (2026-07-24)** 및 사전등록 개정

안 C(§7-C)를 사전등록에 **편입 확정**한다. (b) 조항("분기 1개 후보만 검정")은 아래 (b′)로 **개정 확정**된다.

**정당성** `[Claude 의견]` — (1) **결과를 보기 전**의 후보 추가이므로 사전등록 위반이 아니라 정상 개정이다(위반은 결과를 본 뒤 추가·교체). (2) **선정 근거가 성과와 무관**하다(§7-C-5, 간격 균등성·데이터 age는 결정론적 속성). (3) **축이 다르다** — 안 A는 빈도 축, 안 C는 위상 축이라 (b)의 취지("한 축을 그리드로 훑지 말 것")를 위반하지 않는다. (4) **한 번의 DART 수집이 두 후보를 모두 지원**한다(안 C ⊂ 안 A, §7-D).

> **(b′) 확정 — 캘린더 후보는 정확히 2개로 고정한다: 안 A(빈도 축)·안 C(위상 축).** 각 축에서 후보를 추가·교체하지 않는다. 다른 앵커 부분집합(`{4월,11월}`·`{5월,8월}` 등)과 다른 빈도(월별·격월·6주)의 **성과 실행을 금지**한다. 두 후보가 모두 실패하면 캘린더 축 전체를 종결한다.

**대가**: 후보가 2개면 인컴번트 대비 우연히 δ를 넘을 확률이 대략 2배다. §9-6 (a)(δ 유지 + 자동선택 금지, **거버넌스 규칙**)로 통제한다 — 통계적 다중검정 보정이 아님을 명확히 한다(§9-6).

## 2. 비용 사전 추정 (엔진 상수 기준)

`[검증된 사실]` SPEC_11 §4: `F_pbr_no_r3r4`의 구간당 평균 회전율 **80%** (모멘텀 없는 `D_` 대조군은 52%).

**`[검증된 코드 사실]`** 비용 SSOT는 SPEC_04 문서값이 아니라 **현 엔진 상수**다(§0-A DEBT-1). `engine.py:110-112`가 소비하는 것은 `tc = turnover × (COST_SELL + COST_BUY)`이고, `constants.py`에서 **`COST_SELL + COST_BUY = 0.68%`**(KOSPI/KOSDAQ 미구분)다. 교체 1회당 왕복비용 = turnover 1.0 기준 **0.68%**.

| 시나리오 | 구간당 회전율 | 연간 리밸런싱 | 연간 거래비용 |
|---|---|---|---|
| 현행 반기 | 80% | 2회 | 2 × 0.80 × 0.68% ≈ **1.09%** |
| 분기 (회전율 유지) | 80% | 4회 | 4 × 0.80 × 0.68% ≈ **2.18%** |
| 분기 (회전율 감소) | 55% | 4회 | 4 × 0.55 × 0.68% ≈ **1.50%** |

**분기 증분 비용 = 약 +0.4 \~ +1.1%p/년.** 안 A는 이만큼을 gross로 벌어야 net에서 손해를 안 본다. 이 하한이 QG3 마진(§9-2) 해석의 근거다. **안 C는 연 2회로 현행과 동일해 이 증분이 없다**(단 §7-C-4: 시점·재무가 달라 실제 회전율 차이는 미측정).

`[확실하지 않은 사실]` 실제 분기 회전율은 미측정 — 본 실행에서 측정. **turnover 정의는 `CORR-METRIC-001` 수정 완료분(0.5×Σ|Δw|)을 쓴다.**

`[Claude 의견]` DEBT-1이 코드를 SPEC_04 방향(왕복 ~1.03%, 시장 구분)으로 고치기로 확정되면 이 표는 다시 커지며, QG3 비교 기준선을 확정 SSOT 값으로 재기준화한다.

## 4. TTM 정의 확정 (핵심)

### 4-1. 산식

DART 중간보고서 손익·현금흐름은 **연초부터의 누적(YTD)**이다. Q1=1\~3월, H1=1\~6월, Q3=1\~9월, FY=1\~12월.

| 기준 시점의 최신 보고서 | IS/CF 계정 TTM |
|---|---|
| FY_y | `FY_y` |
| Q1_{y+1} | `FY_y − Q1_y + Q1_{y+1}` |
| H1_{y+1} | `FY_y − H1_y + H1_{y+1}` ← **현행 구현과 동일** |
| Q3_{y+1} | `FY_y − Q3_y + Q3_{y+1}` |

**BS 계정**(자산총계·부채총계·자본총계·지배기업소유주지분·재고자산·매출채권·차입금 계정군)은 스톡 변수이므로 **최신 보고서 스냅샷 그대로** 사용. TTM 미적용. — 현행 `load_pit_series_ttm()` 규약과 동일하므로 **분기 확장은 케이스 추가**이지 로직 교체가 아니다.

### 4-2. `[VERIFY-TTM-000]` — **최대 위험: 연도 위치 정렬**

**이것이 §4에서 가장 위험한 항목이다** — "누적 vs 3개월"(§4-2b)보다 크고 조용하다.

`[검증된 코드 사실]` `backtest/data_access.py::load_pit_series`는 연도 키를 버리고 **위치 리스트**를 반환한다:
```python
sorted_years = sorted(year_dict.keys(), reverse=True)[:n_years]
result[ticker] = [year_dict[yr] for yr in sorted_years]   # 연도 라벨 소실
```
그리고 `load_pit_series_ttm`은 이 리스트 위치가 **연속 연도라고 가정**해 계산한다:
```python
_make_ttm(fyp,   h1c,  h1p)    # fy[0], h1[0], h1[1] 이 같은 연도 축이라 가정
_make_ttm(fypp,  h1p,  h1pp)
```

**한 종목에서 중간 연도(예: H1_2021)가 하나 누락되면 리스트 위치가 당겨져 `FY_2021 − H1_2020 + H1_2022` 같은 잘못된 조합이 조용히 만들어진다.** 예외도 경고도 없다. Q1/Q3는 반기·연간보다 결측 확률이 높으므로(§5-5 검토 미이행 가능성), 이 위험이 **분기 전환에서 구조적으로 확대**된다.

**처리 (§0-A DEBT-2, 외부 계약 보존)**: **내부 로더만** 연도 키 dict로 바꾼다. 외부 `load_pit_series_ttm()`은 `[current, previous, previous2]` 위치 계약을 **그대로 유지**(필터들이 이 계약에 의존하므로 공개 인터페이스를 바꾸면 수정 범위가 폭증). 내부에서만 명시적 연도 조회:
```python
load_pit_by_year()    → {ticker: {year: accounts}}          # 내부 신규
load_pit_series_ttm() → {ticker: [current, prev, prev2]}    # 외부 계약 유지
TTM_y = FY_{y-1} − interim_{y-1} + interim_y                # 위치 아닌 연도로
```
**필수 계정 누락 시에만 제외** (무조건 전체 제외 아님). 채택 파이프라인 필수 계정:
- PBR·R1·R2: 자본·부채·차입금 (BS)
- R5: CFO·재무CF (CF)
- R6: NI·CFO·자본 (IS·CF/BS)

필수 계정이 하나라도 없으면 `ttm_missing_required_account`로 사유 기록 후 해당 룰에서 종목 제외. 선행 PR(DEBT-2)로 분리, QG0은 그 위에서 돈다(§8).

### 4-2b. `[VERIFY-TTM-001]` — 누적 vs 3개월

**`[검증된 코드 사실]`** `ingest/dart_ingest.py` **자체가** 중간보고서(H1·Q1·Q3) IS·CF에서 `thstrm_add_amount`(누적)를 우선 저장하고 BS는 `thstrm_amount`를 쓴다. `api/routers/financials.py::_calc_ttm_metrics`도 `TTM = 최신중간누적 + FY(n-1) − 전년동기누적`으로 이 규약을 쓴다. **즉 규약은 이미 stock-backtest 계열에 존재한다.** 다만 Q1/Q3 수집 경로는 실행된 적이 없으므로(§5-1) 신규 수집·리팩터링 후 회귀 검증이 필요하다.

- **Q3에서 3개월값(7\~9월)을 누적(1\~9월)으로 착각하면 TTM이 조용히 틀린다.** H1이 도는 것은 Q3가 도는 보장이 아니다.

**검증은 항등식이 아니라 fixture로 한다.** `Q1+(H1−Q1)+(Q3−H1)+(FY−Q3)=FY`는 중간항이 소거되어 **어떤 값이든 항상 성립** — 3개월값이 섞여도 통과하므로 검출력이 없다. 대신:

**교체안 ① 코드 오라클 (fixture, 100% 통과 요구)** — 서로 다른 값의 API fixture로 저장 로직을 직접 검증:
```python
item = {"thstrm_add_amount": "900",  # 1~9월 누적
        "thstrm_amount":     "300"}  # 7~9월 3개월
# Q3 IS/CF 저장값이 반드시 900이어야 한다 (누적 우선). 900이 아니면 3개월값 혼입.
```
- FY·BS → `thstrm_amount`
- H1·Q1·Q3의 IS/CF → `thstrm_add_amount`
- `thstrm_add_amount` 결측 시 `thstrm_amount` fallback 여부도 별도 정책화(§10 M2)
- **`thstrm_add_amount != thstrm_amount`인 표본을 의도적으로 포함.** 코드 fixture는 **100% 통과**가 정상.

**교체안 ② 운영 DB 원문 대조 (임계치 99%)** — 표본 공시의 원본 API payload와 저장값을 직접 비교. report_type별 × 핵심 계정별(매출액·영업이익·당기순이익·CFO). **99% 같은 임계치는 이 원문 대조율에만 적용**(§10 M3). 미달 시 Q-A 이후 단계 **중단**.

**annualization fallback 금지**: `[검증된 코드 사실]` 현행 `_make_ttm`에 `FY 없으면 h1c_val * 2` fallback이 있다. **H1을 포함한 모든 중간보고서에서 연율화를 제거**한다. `FY_{y-1}` / `interim_{y-1}` / `interim_y` 중 하나라도 없으면 → 해당 TTM 계정 없음 → 필수 룰에서 명시적 제외(§4-2 필수 계정 규칙). `Q1×4`·`Q3×4/3`·`H1×2` 전부 금지.

### 4-3. `[VERIFY-TTM-002]` — 3개년 시계열의 단위 일관성

`[검증된 사실]` `load_pit_series_ttm()`은 `[ttm_curr, ttm_prev, ttm_pp]` 3개를 반환하고, `stability_filter`는 `series[1]`·`series[2]`를 참조한다.

채택 룰셋 `{R1, R2, R5, R6}`의 실제 의존도:

| 룰 | 계정 성격 | 다년 시계열 필요 | 분기 전환 시 변화 |
|---|---|---|---|
| R1 부채비율 | BS/BS | 불필요 | **BS 갱신 빈도 2배** |
| R2 차입금비율 | BS/BS | 예외조항(3FY 단조감소)만 필요 | BS 갱신 빈도 2배 |
| R5 CFO<0 & FinCF>0 | CF | 불필요 | **TTM 적용의 최대 수혜** (§4-4) |
| R6 adjROE < r | IS·CF / BS | 불필요 | **TTM 적용의 최대 수혜** |
| 랭킹 1/PBR | 가격 / BS | 불필요 | 분모(BV)만 갱신 빈도 2배 |

`[Claude 의견]` **분기 전환이 실제로 바꾸는 것은 생각보다 좁다.** 랭킹 신호 1/PBR의 분자(가격)는 이미 매일 갱신 중이고, 분기 전환은 분모(장부가)의 갱신 주기와 R5/R6 판정의 신선도, 그리고 리밸런싱 자체의 빈도를 바꾼다. 기대 효과를 여기에 맞춰 잡아야 한다.

**데이터 시작점 제약**: `ttm_prev`(1년 전 동일 분기 TTM)를 만들려면 그 시점의 FY와 전전년 동일 분기가 필요하다. `[검증된 사실]` `financials`는 2015년부터 수집되어 있고 2014년은 미수집(MASTER v5.2 — 현행 TTM 제약의 실제 원인). 따라서 **분기 유효 구간의 시작이 반기(2016-04-05)보다 늦어질 가능성이 높다.**

- **필수 산출물**: Q-B 완료 직후 "분기 앵커별 유효 종목 수" 표를 만들어 **유효 구간 시작일을 확정**한다.
- 반기 20구간과 분기 N구간의 **기간이 다르면 CAGR 비교가 성립하지 않는다.** §9의 모든 비교는 **공통 기간으로 절단**한 뒤 수행한다. 이 절단 규칙은 결과 열람 전에 사전등록한다.

### 4-4. R5의 계절성 — TTM을 쓰는 실질적 이유

`[Claude 의견]` R5(`영업CF < 0 AND 재무CF > 0`)를 **YTD 원값**으로 판정하면 Q1 시점에서 오탐이 급증한다. 1분기 운전자본 유출로 CFO가 음수인 정상 기업이 대량으로 "차입 운영"으로 탈락한다. TTM은 이 계절성을 구조적으로 제거한다. R6의 adjROE도 동일. **"판정 기준을 TTM으로"라는 방향은 정확하며, 사실상 필수 조건이다.**

`"1분기보고서"`/`"3분기보고서"` 문자열은 **존재하지 않는다.** 따라서 수정 전 매핑은 Q1/Q3에
**0건 매칭**되고, 결과적으로:

- `disclosures`에 Q1/Q3 행이 생기지 않음 →
- `pit_loader.resolve_dates()`가 fallback 경로로 →
- **전 종목 Q1/Q3의 `available_from`이 법정마감+5일 고정, `fallback_used=TRUE`**

H1 공시 누락 52% 사태(`scripts/fix_h1_disclosures.py`)와 정확히 같은 함정이 **100% 발생률로
확정 재현**된다. fallback은 **실제 공시일보다 항상 늦으므로 룩어헤드는 없고**, 조용히 유니버스만
축소시킨다 — 경고 없는 왜곡.

**수정 (2026-07-27 적용)** — `_upsert_disclosures`를 다음으로 교체:
1. 카테고리는 한글 명칭 substring으로 판정(`[기재정정]` 접두 자동 흡수). `분기보고서`는 별도 분기.
2. Q1/Q3 구분은 **1순위 `report_nm`의 `(YYYY.MM)` 대상월 파싱**(`.03`→Q1, `.09`→Q3, 12월 결산),
   파싱 실패 시 **`rcept_dt` 구간 fallback**(Q1 = 4\~8월 접수, Q3 = 10\~익2월 접수 — stock-analysis
   `dart_collector._REPRT_DATE_RANGES` 이식). §5-6 우선순위(파싱 > fscl_month > 접수일)와 정합.
3. **FY/H1 경로·연도 역산은 비트 단위로 불변** — 인컴번트 disclosures 행은 재수집해도 바뀌지 않는다.
4. 비12월 결산(`(YYYY.06)`/`(YYYY.12)` 분기보고서)은 파싱 {3,9} 밖 → rcept fallback로 흐르며,
   §5-6(VERIFY-INGEST-004)에서 별도 처리·제외.

**추가 안전장치**: `bsns_year` 역산 로직(`report_type == 'FY' and rcept_date.month <= 6` 분기)의
12월 결산 가정은 FY 경로 그대로 유지하고, Q1/Q3는 대상월 파싱 연도를 우선 사용한다.

### 5-4. `[VERIFY-INGEST-002]` — 수집 대상 (year, report_type) 생성기

### 7-3. 캘린더 주입 — `RebalancePoint` 스케줄 객체

**`[검증된 코드 사실]`** 현행 엔진의 보고서 유형 선택은 월 추론이다:
```python
def _report_type(d: date) -> str:
    return 'H1' if d.month == 8 else 'FY'   # engine.py — validate/factor_comparison.py에 복제본도 존재
```
**이 상태로 분기 날짜만 추가하면 5월·11월이 전부 FY로 조용히 처리된다.** Q1/Q3 재무를 수집해도 엔진이 쓰지 않는다. 단순한 `rebalance_freq='quarterly'` 플래그는 이 월 추론을 우회하지 못한다 — 스케줄에 report_type을 **명시적으로 실어야** 한다.

**설계**: 날짜 리스트 대신 `RebalancePoint`를 SSOT로 둔다. `report_type`·`fiscal_year`를 명시 탑재해 `_report_type()` 월 추론을 제거한다.
```python
# backtest/configs/schedule.py (신규)
from dataclasses import dataclass
from datetime import date
from typing import Literal

@dataclass(frozen=True)
class RebalancePoint:
    date:              date
    report_type:       Literal["FY", "Q1", "H1", "Q3"]
    fiscal_year:       int    # 이 앵커가 원하는 사업연도 (stale 방지 — DEBT-3)
    nominal_period_end: date  # fiscal_year·report_type이 커버하는 기간 종료일 (age 산출)
    calendar_id:       Literal["SEMIANNUAL", "A", "C"]   # 안 B 제거
```

`fiscal_year` 고정 예시:

| 앵커 | `report_type` | `fiscal_year` |
|---|---|---|
| 2025년 4월 | FY | 2024 |
| 2025년 5월 | Q1 | 2025 |
| 2025년 8월 | H1 | 2025 |
| 2025년 11월 | Q3 | 2025 |

- **`fiscal_year`가 있어야 DEBT-3의 stale 오류를 막는다.** 로더는 `(ticker, fiscal_year, report_type)`을 **정확 조회**하고, 원하는 기간 보고서가 미공개면 그 앵커에서 종목 제외 + `late_or_missing_current_report` 집계(§0-A DEBT-3). `source_period_end`만으로는 2025 Q1과 2024 Q1을 강제 구분하지 못한다.
- `engine.py::_report_type()` **제거** → 엔진은 `RebalancePoint.report_type`·`fiscal_year`를 직접 소비.
- `rebalance_freq`는 외부 CLI 선택값으로만 두고, 엔진에는 항상 `tuple[RebalancePoint, ...]`를 전달.

**필수 수정 목록 (§7-5 grep보다 우선)** — `[검증된 코드 사실]` 다음 네 경로가 반기 캘린더/`_report_type`/고정 START·END에 하드 의존한다:
```
1. engine.py::_report_type()            → 제거, RebalancePoint.report_type 소비
2. validate/factor_comparison.py         → _report_type() 복제본 존재. 동일 처리
3. run_ablation.py                       → REBALANCE_DATES 직접 import
4. export_portfolios.py                  → 전역 날짜 + 고정 START/END + _report_type()
5. scripts/robustness/run_random_pool.py → 날짜·완결구간·보고서유형 전부 반기 고정
```

### 7-3b. 생성기 — `scripts/generate_rebalance_dates.py` 확장

기존 스크립트에 `--freq`·`--as-of`를 추가한다. **기존 동작(반기)이 기본값이며 무변경.**

**`--as-of` 필수 (재현성).** `[검증된 코드 사실]` 엔진이 `CORR-ENGINE-003`으로 `date.today()` 내부 호출을 금지하고 `valuation_date` 주입을 강제하므로 생성기도 같은 원칙을 따른다. `--as-of`를 빼면 2026-08-19가 지나는 순간 반기 오라클이 23개가 아니라 24개가 되어 실패한다.

```python
# scripts/generate_rebalance_dates.py  (확장)
#
#   python scripts/generate_rebalance_dates.py --as-of 2026-07-24                  # 반기 (기존, 23개)
#   python scripts/generate_rebalance_dates.py --as-of 2026-07-24 --freq quarterly # 안 A (46개)
#   python scripts/generate_rebalance_dates.py --as-of 2026-07-24 --verify         # 오라클만
#
# 영업일 캘린더 = price_history DISTINCT date (pykrx get_index_ohlcv_by_date는 KRX 2024 리뉴얼 후 불작동)
import argparse
from datetime import date, timedelta
from ingest.connection import db_conn

# (월, 일, report_type) — fiscal_year·nominal_period_end는 출력 시 산출
DEADLINES = {
    'semiannual': [(3, 31, 'FY'), (8, 14, 'H1')],
    'quarterly':  [(3, 31, 'FY'), (5, 15, 'Q1'), (8, 14, 'H1'), (11, 14, 'Q3')],
}
OFFSET = 3  # 법정마감 + 3영업일

KNOWN_SEMIANNUAL = [   # 오라클 기준 (backtest/configs/rebalance_dates.py 현행값)
    date(2015,4,3), date(2015,8,19), date(2016,4,5), date(2016,8,18),
    date(2017,4,5), date(2017,8,18), date(2018,4,4), date(2018,8,20),
    date(2019,4,3), date(2019,8,20), date(2020,4,3), date(2020,8,20),
    date(2021,4,5), date(2021,8,19), date(2022,4,5), date(2022,8,18),
    date(2023,4,5), date(2023,8,18), date(2024,4,3), date(2024,8,20),
    date(2025,4,3), date(2025,8,20), date(2026,4,3),
]

def nth_trading_day_after(cur, base: date, n: int) -> date:
    cur.execute(
        "SELECT DISTINCT date FROM price_history "
        "WHERE date > %s AND date <= %s ORDER BY date LIMIT %s",
        (base, base + timedelta(days=45), n),
    )
    rows = cur.fetchall()
    if len(rows) < n:
        raise ValueError(f'거래일 부족: base={base}, found={len(rows)}, need={n}')
    return rows[n - 1][0]

def build(cur, freq: str, as_of: date, start_year=2015, end_year=2026):
    out = []
    for yr in range(start_year, end_year + 1):
        for mo, dy, rtype in DEADLINES[freq]:
            d = nth_trading_day_after(cur, date(yr, mo, dy), OFFSET)
            if d <= as_of:                 # date.today() 아님 — 주입된 as_of
                out.append((d, rtype))
    return sorted(out)

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument('--as-of', required=True, type=date.fromisoformat)  # 필수 (재현성)
    ap.add_argument('--freq', choices=['semiannual', 'quarterly'], default='semiannual')
    ap.add_argument('--verify', action='store_true')
    args = ap.parse_args()

    with db_conn() as conn:
        cur = conn.cursor()
        # 오라클: 어떤 모드든 항상 먼저 반기 재현 검증
        semi = [d for d, _ in build(cur, 'semiannual', args.as_of)]
        if semi != KNOWN_SEMIANNUAL:
            diff = [(a, b) for a, b in zip(semi, KNOWN_SEMIANNUAL) if a != b]
            raise SystemExit(f'❌ 오라클 실패 — 반기 재현 불일치 {len(diff)}건: {diff[:5]}')
        print(f'✅ 오라클 통과 — 반기 {len(semi)}개 재현')
        if args.verify:
            return

        pts = build(cur, args.freq, args.as_of)
        if args.freq == 'quarterly':
            missing = set(KNOWN_SEMIANNUAL) - {d for d, _ in pts}
            if missing:
                raise SystemExit(f'❌ 상위집합 위반 — 누락 반기 앵커: {sorted(missing)}')
            print(f'✅ 상위집합 검증 통과 — 반기 앵커 {len(KNOWN_SEMIANNUAL)}개 포함')

        # RebalancePoint 형태로 출력 (calendar_id·fiscal_year는 명시 매핑)
        CALENDAR_ID = {'semiannual': 'SEMIANNUAL', 'quarterly': 'A'}  # freq[:1].upper() 금지
        for d, rtype in pts:
            fy = _fiscal_year(d, rtype)   # FY→해당 연도-1, Q1/H1/Q3→해당 연도
            print(f'    RebalancePoint(date({d.year},{d.month},{d.day}), "{rtype}", '
                  f'{fy}, {_nominal_period_end(fy, rtype)!r}, "{CALENDAR_ID[freq]}"),')

if __name__ == '__main__':
    main()
```

> `[Claude 의견]` `nth_trading_day_after()`는 기존 파일 함수를 재사용한다(중복 정의 금지). **`args.freq[:1].upper()`는 버그였다** — `quarterly`→`"Q"`, `semiannual`→`"S"`를 반환해 설계한 `"A"`·`"SEMIANNUAL"`과 어긋난다. 명시적 `CALENDAR_ID` 매핑으로 교체했다.

### 7-4. `rebalance_dates.py` 반영 형태 — 이중 SSOT 제거

스케줄이 SSOT, 날짜 리스트는 **파생 뷰**다. 날짜 리스트를 별도 하드코딩하면 날짜와 report_type이 따로 수정될 수 있으므로 금지.

```python
# backtest/configs/rebalance_dates.py

REBALANCE_DATES: list[date] = [ ... 23개 그대로 ... ]

# ── 신규 SSOT: RebalancePoint 스케줄 (생성기 출력 하드코딩) ────────────────

REBALANCE_SCHEDULE_A: tuple[RebalancePoint, ...] = (

    RebalancePoint(date(2015,8,19), "H1", 2015, date(2015,6,30),  "A"),

)

# 반기 어댑터 — 기존 날짜를 그대로 감싸 생성 (레거시 호환)
REBALANCE_SCHEDULE_SEMIANNUAL = build_legacy_schedule(REBALANCE_DATES)

# ── 파생 뷰 (날짜만 필요한 레거시 소비처용 — 하드코딩 아님) ────────────────
REBALANCE_DATES_Q = tuple(p.date for p in REBALANCE_SCHEDULE_A)   # 46개
REBALANCE_DATES_C = tuple(p.date for p in REBALANCE_SCHEDULE_C)   # 23개

# ── 불변식 assert (import 시) ─────────────────────────────────────────────

assert set(REBALANCE_DATES_C) <= set(REBALANCE_DATES_Q), '안 C ⊂ 안 A 위반'
```

**핵심**: 날짜와 report_type·fiscal_year가 **한 곳(스케줄)에서만** 정의된다. 파생 뷰는 스케줄에서 계산되므로 둘이 어긋날 수 없다. §7-1 산출 날짜(오라클 통과)와 §4-1 TTM 매핑이 스케줄 리터럴에 함께 박힌다.

## 7-C. 안 C — `{Q1(5월), Q3(11월)}` 반기 (사용자 제안, 2026-07-24)

### 7-C-1. 착상

현행 반기는 **`{Q1,Q2}` 묶음과 `{Q3,Q4}` 묶음**을 각각 그 묶음의 **첫 정보 시점**에서 실행한다 — 4월 앵커는 FY 보고서(= Q3+Q4가 마지막으로 반영된 시점), 8월 앵커는 H1 보고서(= Q1+Q2 누적). 사용자 제안은 같은 묶음을 **`{Q4,Q1}`과 `{Q2,Q3}`로 재편**하고, 각 묶음의 **마지막 정보 시점**에서 실행하는 것이다:

- `{Q4, Q1}` 정보가 모두 공개되는 시점 = **Q1 보고서 공시(5/15) → 앵커 5/18\~20**
- `{Q2, Q3}` 정보가 모두 공개되는 시점 = **Q3 보고서 공시(11/14) → 앵커 11/17\~19**

**리밸런싱 빈도는 연 2회로 현행과 동일하다.**

### 7-C-2. 실산출 비교 `[검증된 사실]`

| 안 | 앵커 수 | 간격 (일) | 간격 표준편차 | 데이터 age 평균 | age 표준편차 | 연 리밸런싱 |
|---|---|---|---|---|---|---|
| **현행 반기** {4월, 8월} | 23 | 135 \~ 230 | **45.6** | **73일** | **22.0** | 2회 |
| **안 A 분기** {4,5,8,11월} | 46 | 43 \~ 139 | 32.9 | 61일 | 19.7 | 4회 |
| **안 C 반기** {5월, 11월} | 23 | **181 \~ 185** | **0.9** | **49일** | **1.0** | **2회** |

*데이터 age = 앵커일 − 그 시점 TTM이 커버하는 재무 종료일. 작을수록 신선.*

앵커별 데이터 age 분해:

| 앵커 | 사용 TTM | age |
|---|---|---|
| 현행 4월 | `FY_{y-1}` (Q1 아직 미공시) | **94일** |
| 현행 8월 | `FY−H1_prev+H1_curr` | 50일 |
| 안 A 5월 | `FY−Q1_prev+Q1_curr` | 49일 |
| 안 A 11월 | `FY−Q3_prev+Q3_curr` | 49일 |
| **안 C** 5월·11월 | 위와 동일 | **49일 (균일)** |

### 7-C-3. 판단 `[Claude 의견]`

**두 안은 서로 다른 목적의 비중첩 후보이며, 데이터 신선도는 어느 지표로 재느냐에 따라 우열이 갈린다.**

**두 종류의 데이터 age를 구분해야 한다** `[검증된 사실 — 독립 재계산]`:

| 지표 | 재는 것 | 현행 | 안 A | 안 C |
|---|---|---|---|---|
| **앵커시점 age**(보유가중) | 포트폴리오를 **고르는 순간**의 정보 신선도 | 66.6일 | 54.9일 | **49.0일** |
| **보유기간 가중평균 age** | **평균적인 하루**의 포지션 정보 신선도 | 163일 | **106일** | 140일 |
| **최대 stale 기간** | 가장 낡은 순간 | 277일 | **186일** | 232일 |

`[Claude 의견]` **안 C가 앞의 한 축(의사결정 신선도)을, 안 A가 뒤의 두 축(포지션 품질·최대 노후)을 이긴다.** 안 A가 보유가중에서 앞서는 이유는 연 4회 갱신하기 때문이다 — 리밸런싱 순간의 age가 다소 높아도(4월 앵커의 94일 FY 단독 데이터 때문), 보유 기간 전체로는 더 자주 새로고침한다. 두 지표 모두 정당하다 — **안 C는 앵커시점 age만, 안 A는 보유가중·최대 stale을 이긴다.**

안 C가 명확히 우위인 축은 남아 있다:

1. **추가 이벤트 비용**: 안 C는 연 2회로 현행과 동일 → 리밸런싱 **이벤트 수 증가에 따른 사전적 비용이 0**. (단 §7-C-4 ①: 시점·재무가 달라져 편입·회전율은 달라지므로 "실제 비용 차이 0"은 아니다.)
2. **간격 균등성**: 표준편차 0.9일(181\~185일). 사실상 완벽한 반기라 구간 통계·paired 부트스트랩·CAGR 환산이 깔끔하다. **단 이는 측정을 깔끔하게 할 뿐 수익을 만들지 않는다**(§7-D 사전 예측).

안 A가 명확히 우위인 축:

- **재평가 빈도**: 연 4회 → 모멘텀 거부권 발동 기회 2배. 안 A의 유일한 알파 가설.
- **보유가중 age·최대 stale**: 위 표.
- **상위집합 성질**: 안 A ⊃ 현행 → "동일 앵커 + 2회 추가"의 순수 증분 해석. 안 C는 현행과 앵커 교집합 0이라 **위상(phase) 효과** 비교가 된다.

**결론**: 안 C와 안 A는 **서로 다른 질문에 답하는 비중첩 후보**다(§7-D). 어느 쪽도 상대를 지배하지 않는다.

### 7-C-4. 안 C의 실질 비용 — 과소평가 금지

**(a) "추가 거래비용 0"이 아니라 "추가 이벤트 0, 실제 차이 미측정".** `[Claude 의견]` 안 C는 리밸런싱 **이벤트 수**가 현행과 같아 "이벤트 증가에 따른 사전적 비용 하한"이 없을 뿐, **리밸런싱 시점과 재무 데이터가 달라 편입 종목·회전율이 달라진다.** 인컴번트 대비 실제 회전율·거래비용 차이는 **미측정**이며 본 실행에서 측정한다.

**(b) DART 수집 임계경로는 그대로다.** `[검증된 코드 사실]` 안 C의 두 앵커 모두 Q1·Q3 보고서를 쓴다. `TARGET_REPORTS`가 FY/H1뿐이므로(§5-1) **§5의 15\~25일 수집이 안 C에도 100% 필요하다.** "빈도를 안 늘리니 싸다"는 거래비용 얘기지 데이터 비용 얘기가 아니다.

**(c) #24 라이브 트랙과 어긋난다.** `[검증된 사실]` §7-6대로 #24(2026-08-19)는 안 A에서는 H1 앵커로 존재하지만 **안 C에는 8월 앵커가 없다.** 안 C 채택 시 라이브 첫 앵커는 **2026-11-18**로 약 3개월 지연된다.

`[Claude 의견]` #24는 프로젝트 최초의 진짜 OOS 관측으로 사전등록까지 마친 자산이다. #24 기록 자체는 인컴번트의 OOS 관측으로 여전히 유효하지만, **안 C는 11월까지 라이브 근거가 0인 상태로 남는다.** 이것이 안 C의 가장 현실적인 비용이며, 안 A의 가장 큰 실무적 강점이다.

### 7-C-5. 캘린더 선정이 in-sample 최적화가 아닌 이유

`[Claude 의견]` 4개 앵커의 2개짜리 부분집합은 6가지다. 그중 안 C를 고른 근거는 **간격 균등성과 데이터 age — 둘 다 성과와 무관한 결정론적 속성**이다. §7-C-2 표는 어떤 수익률도 참조하지 않고 계산됐다. **성과를 보고 캘린더를 고르는 순간부터가 데이터 스누핑이고, 그 선을 넘지 않았다.**

이 원칙을 유지하기 위해 **나머지 부분집합의 성과 실행을 명시적으로 금지**한다. 특히 §7-C-2 계산 과정에서 간격 통계만 산출된 `{4월, 11월}`(135\~230일, 현행과 사실상 동일)과 `{5월, 8월}`(91\~276일, 현행보다 나쁨)은 **성과 실행 대상이 아니다.** 두 안은 결정론적 기준에서 이미 열등하므로 후보가 아니다.

### 7-C-6. 안 C 앵커 목록 — 파생 뷰

**하드코딩하지 않는다.** §7-4의 이중 SSOT 제거 원칙대로, 안 C는 안 A 스케줄의 `{Q1,Q3}` 부분집합으로 **파생**된다:

## 9. 판정 기준 — 사전등록 (2026-07-24 확정, 결과 열람 후 수정 금지)

### 9-1. 대조군은 후보 캘린더별로 각각 재생성 + metric 정의 통일

`[Claude 의견]` **반기 캘린더로 만든 `C_pbr_path_random`의 p95를 분기 전략과 비교하면 안 된다.** 빈도가 다르면 랜덤 귀무분포 자체가 달라진다(비용 구조·복리 경로 모두).

- `C_pbr_path_random_A` / `_C`: **해당 캘린더로 1,000회 재추첨**, seed 체계·holdings 보존 동일 (`random.Random(f"{seed}:{date}")`).
- `U_pbr_path_ew_A` / `_C`: 동일 필터 통과 전 종목 동일가중, 해당 캘린더.
- 비교 기간은 §9-2b 공통 기간 규칙 적용. **인컴번트 태그도 같은 기간으로 재산출**(공표값 그대로 인용 금지).

**`[검증된 코드 사실]` net CAGR 정의를 일별 NAV와 통일한다.** 현행 `run_random_pool.py`는 `net = gross − tc`(산술)인데, 일별 NAV 엔진은 리밸런싱일 `NAV × (1 − tc)`(승법)라 구간 net이 `gross − tc − gross×tc`로 다르다. 이는 SPEC_09 CONTRACT-NAV-003에 명문화된 정의 차이이며 07-20 실행에서 교차항 drag가 net CAGR −0.03\~0.08%p로 실측됐다. **QG1이 일별 net NAV CAGR을 산술 정의 랜덤 p95와 비교하면 δ=0.1%p 문턱에서 두 정의가 섞인다.**

**수정**: 랜덤 1,000회도 일별 경로를 전부 만들 필요 없이 **terminal NAV만 승법으로** 계산한다:
```python
net_growth *= (1 - tc) * (1 + gross)     # 산술 net=gross−tc 폐기
net_cagr = net_growth ** (1 / years) - 1
```
임의 seed 1개를 전체 일별 NAV 엔진으로 돌려 terminal NAV가 `1e-12` 이내 일치하는지 **등가성 게이트** 추가.

> **QG1\~QG3 metric SSOT (사전등록)**: 후보·인컴번트·랜덤·EW 전부 **일별 NAV와 동일한 승법 거래비용 정의**로 계산한 CAGR·Sharpe·MDD를 쓴다. 산술 `gross − tc` 정의는 어디에도 쓰지 않는다.

### 9-2. 하드 게이트 (전부 충족 시에만 "캘린더 전환 후보"로 상신) — 각 후보에 독립 적용

각 후보(안 A·안 C)에 **독립 적용**한다. `F_..._X`는 해당 캘린더 태그, 대조군도 그 캘린더로 재생성한 것(§9-1)을 쓴다.

| # | 기준 | 성격 |
|---|---|---|
| **QG0** | 배관 게이트 (§8) 통과 | 결과 신뢰의 전제 — **캘린더 품질과 무관, 리팩터링 무결성** |
| **QG1** | `F_..._X` 일별 net CAGR > `C_pbr_path_random_X` **p95** | 캘린더 품질 — 랜덤 대비 |
| **QG2** | `F_..._X` 일별 net CAGR > `U_pbr_path_ew_X` net CAGR | 캘린더 품질 — EW 대비 |
| **QG3** | `F_..._X` 일별 net CAGR ≥ 인컴번트 net CAGR **+ 0.1%p** (공통 기간, §9-2b) | 캘린더 품질 — 복잡도 프리미엄 |
| **QG5-PROD** | 일별 net MDD가 **−45%**보다 얕음 (SPEC_09 엔진) | **프로덕션 적격성 — 캘린더 효과의 증거가 아님** |

QG5-PROD는 "캘린더가 좋은가"의 증거가 아니라 "프로덕션 후보가 갖춰야 할 상위 리스크 한계"다. 성격이 다르므로 **QG5-PROD**로 이름만 분리하되 **−45% 한계선과 삭제 금지는 그대로**다(§9-5 불간섭 조항 유지). `[검증된 코드 사실]` 반드시 `engine.metrics['mdd']`(리밸런싱 종점 기반)가 아니라 **일별 NAV MDD**(`compute_daily_metrics`)를 쓴다 — 07-20 결과에서 이 둘이 −30.7% vs −54.2%로 갈렸다.

**δ = +0.1%p** `[확정 2026-07-24]`. 거래비용은 §2에서 엔진 상수 기준 **연 +0.4\~1.1%p**(안 A)로 이미 net에 반영되어 있으므로, δ는 순수하게 "Q1/Q3 데이터 품질 리스크 + 운영 복잡도(안 A는 2배) + 검토 수준이 낮을 수 있는 재무제표 의존"의 대가다. **안 C는 이벤트 비용이 없으므로 δ의 의미가 안 A와 다르지만**(순수 위상 효과의 대가), 다중검정 위생상 **두 후보 동일 δ=0.1%p**를 유지한다(§9-6 (a)).

`[Claude 의견]` δ=0.1%p의 **실질적 파급 하나를 명시해 둔다**:

> **δ가 작을수록 공통 기간 규칙(§9-2b)이 판정을 좌우한다.** CAGR은 시작·종료 시점을 몇 구간만 옮겨도 0.1%p를 쉽게 넘나든다. δ=0.5%p였다면 절단 규칙의 세부는 대체로 판정을 뒤집지 못했겠지만, **δ=0.1%p에서는 절단 규칙 자체가 판정 변수**가 된다.

따라서 **공통 기간 규칙(§9-2b)은 QG3와 동급의 사전등록 대상**이다. Q-B 완료 직후(분기 유효 시작일 확정 시점, **그러나 어떤 성과 수치도 산출하기 전**) 규칙을 문서로 고정하고 이후 수정하지 않는다.

`[Claude 의견]` 아울러 δ=0.1%p는 사실상 "거의 동률이면 분기 채택"에 가까운 문턱이다. 이 선택 자체는 사용자 권한이고 사전등록된 이상 그대로 집행하지만, **QG3를 아슬아슬하게 통과하는 결과(예: +0.12%p)가 나올 경우 그것을 "분기가 낫다"의 증거로 읽지 말 것**을 미리 기록해 둔다. 그 구간의 결론은 "구분되지 않는다"이며, §9-4의 상신 문안에도 마진 수치를 반드시 병기한다.

#### 9-2b. 공통 기간 — warm-up 후 NAV 정규화 (강제 거래 금지)

`[검증된 코드 사실]` 엔진은 각 캘린더의 첫·마지막 완결 구간으로 CAGR을 계산한다. **안 C와 인컴번트는 앵커 교집합이 0이므로 "공통 연도만 절단"으로는 부족하다.**

**공통 시작일에 강제 매수하지 않는다** — 안 C의 예정 리밸런싱일이 아닌 날짜에서 새로 매수하면 원래 전략에 없던 리밸런싱을 하나 추가하는 셈이다(첫 진입 비용도 후보별로 달라짐 — DEBT-4). **warm-up 후 정규화**:

> **확정 규칙:**
> 1. 성과와 무관한 규칙으로 공통 평가 시작일 `S`·종료일 `E` 결정.
> 2. 각 전략은 `S` **이전 자신의 마지막 정상 앵커부터** 실제 캘린더대로 시뮬레이션(warm-up).
> 3. `S`에서 **거래하지 않고**, 당시 보유 포트폴리오·NAV를 그대로 승계.
> 4. `NAV(S) = 1.0`으로만 **정규화**(강제 매수 아님).
> 5. `(S, E]`의 일별 net NAV로 공식 CAGR·Sharpe·MDD 계산.

**정규화는 허용, 공통 시작일의 강제 매수는 금지.** 정책 자체는 Q-A 전에 동결하고, 정확한 `S`·`E` 날짜는 Q-B에서 데이터 가용성 확인 후 기계적으로 대입한다.

`[검증된 코드 사실]` 일별 net NAV 함수는 SPEC_09에 존재한다. 캘린더 간 공식 비교는 구간 CAGR이 아니라 이 일별 net NAV(승법 비용, §9-1) 기준이다.

- **leave-one-year-out / leave-one-period-out** 안정성
- **`P(ΔCAGR > 0)`와 `P(ΔCAGR > 0.1%p)`** — δ 문턱 넘을 확률의 부트스트랩 추정

**Sharpe 정정.** `[검증된 코드 사실]` `metrics.py`의 `PERIODS_PER_YEAR = 2`와 `compute_sharpe`의 `RF/2`·`√2`는 반기 구간용이다. 분기 캘린더를 넣어도 엔진은 이 값을 별도 전달하지 않고, 안 A는 구간 길이가 43\~139일로 불규칙해 4로 바꾸는 것도 틀리다. **캘린더 간 공식 Sharpe = 일별 net NAV Sharpe**(§9-1 승법 정의). 구간 Sharpe는 참고값으로만 병기.

### 9-4. 판정 규칙

**용어 분리** — "기계적 통과"와 "우월성 확인"의 모순을 없애기 위해 두 라벨을 나눈다:
- **`QG3_SCREEN_PASS`**: 마진 ≥ +0.1%p (문턱 통과). 상신 자격.
- **`evidence_label`**: `SUPERIOR`(마진 큼 + bootstrap 안정) / `INCONCLUSIVE`(+0.1\~+0.3%p 또는 bootstrap 불확실) / `INFERIOR`.

`QG3_SCREEN_PASS`여도 `evidence_label=INCONCLUSIVE`면 **상신은 가능하되 "우월성이 확인됐다"는 표현을 금지**한다.

**판정 분기:**

| 경우 | 판정 |
|---|---|
| QG0 실패 | 즉시 중단. 성과 수치 미발행 |
| QG1·QG2·QG3·QG5-PROD 전부 통과, `evidence=SUPERIOR` | **캘린더 전환 후보 상신** (프로덕션 채택 아님 — 라이브 포워드 확인 후) |
| QG1~QG3 통과, `evidence=INCONCLUSIVE` (+0.1\~0.3%p) | 상신하되 **"우월성 확인" 표현 금지.** 마진·bootstrap 병기 |
| **QG1~QG3 통과, QG5-PROD 실패** | 캘린더 수익 가설은 통과했으나 프로덕션 리스크 미충족. **Research challenger로만 보존**, 운용 후보 상신 금지 |
| **QG3 실패, QG5-PROD도 개선 없음** | 캘린더 후보 탈락. 해당 축 종결 |
| QG5-PROD만 개선, QG3 실패 | 자동 탈락도 채택도 아님. 수치 보고 후 사용자 결정. §1-1 사전 예측과 대조 |
| QG1 또는 QG2 실패 | 반기 유지. **캘린더 축 종결** — 다른 주기·앵커 탐색 금지 (§1-3 b′) |

**두 후보(안 A·안 C) 동시 처리 (§9-6와 연결):**
- **둘 다 통과** → **자동 선택 금지**(max 선택은 편향 추정량). 둘 다 상신, 마진·`evidence_label` 병기, 라이브 포워드로 구분.
- **한쪽만 통과** → 통과한 쪽만 상신. 탈락 축 종결.
- **둘 다 실패** → 인컴번트 유지, 캘린더 축 전체 종결.

어떤 경우든 결과는 보고서로 발행하고 다음 행동은 사용자 결정.

### 9-5. 상위 게이트 불간섭 조항

**본 SPEC의 QG5-PROD 결과는 SPEC_10 G5 판정을 대체하지 않는다.** 분기 전환이 QG5-PROD를 통과해도 `F_pbr_no_r3r4`(반기)의 G5 FAIL 상태는 그대로 유지되며, 분기 전략은 **별도 후보**로서 자체 게이트 이력을 처음부터 쌓는다. 이 조항 없이는 "주기를 바꿔 G5를 통과시켰다"는 게이트 세탁이 된다.

### 9-6. 후보 2개 다중검정 처리 — **확정 (a): δ 유지 + 자동선택 금지 (거버넌스 규칙)**

안 C 편입으로 인컴번트에 도전하는 후보가 2개다.

**(1) 캘린더별 랜덤 귀무분포 — 필요하지만 충분하지 않다** `[Claude 의견]`

§9-1의 후보별 랜덤 대조군은 **"해당 캘린더에서 PBR 랭킹이 랜덤보다 나은가"**만 검정한다. **"안 A·안 C 중 어느 게 인컴번트보다 우연히 좋아 보였나"는 검정하지 못한다** — 달력 효과가 전략·랜덤 양쪽에 공통이라 상쇄되기 때문이다. 후보 선택 편향은 §9-3 paired bootstrap + 아래 (a)로 통제한다.

**(2) 확정: (a) δ 유지 + 자동선택 금지 — 통계 보정이 아니라 거버넌스 규칙**

| 안 | 내용 | 판정 |
|---|---|---|
| **(a) δ=0.1%p 유지 + 자동선택 금지** | 둘 다 통과 시 더 나은 쪽을 자동 채택하지 않음. 둘 다 상신, 라이브로 구분 | **확정** |
| (b) δ 상향(0.1→0.2%p) | Bonferroni 성격 | 비채택 — 확정 δ를 되돌리는 부담, 통계 근거 약함 |
| (c) 후보별 차등 δ | 안 C δ 하향 | 비채택 — δ가 조정 자유도가 됨 |

`[확정 2026-07-24]` **(a)를 채택한다. 이는 통계적 다중검정 보정이 아니라 거버넌스 규칙이다.** 핵심은 **"max 선택 금지"** — 두 후보 중 더 나은 쪽을 고르는 순간 편향 추정량이 되며 n≈20에서 그 편향이 δ=0.1%p보다 클 수 있다. 둘 다 통과하면 **둘 다 미채택 상태로 상신**, 두 마진·`evidence_label` 병기 후 라이브 관측으로 넘긴다. 통계적 근거는 §9-3의 paired block bootstrap·`P(ΔCAGR>0.1%p)`가 제공한다.

## 11. 요약

`[Claude 의견]` **이 실험은 두 층위로 나뉜다 — 후보 구조(무엇을 실험하나)와 실행 무결성(어떻게 안전하게 하나).**

**후보 구조.** **안 A(분기)** 는 연 +0.4\~1.1%p(엔진 상수 기준)의 확정 거래비용과 15\~25일 DART 쿼터를 대가로 재평가 빈도를 2배로 올린다. 알파 가설은 "모멘텀 거부권이 더 자주 발동한다" 하나다. **안 C(`{Q1,Q3}` 반기)** 는 이벤트 비용을 늘리지 않고 앵커시점 데이터 age(66.6→49일)와 간격 균등성(σ 45.6→0.9일)을 개선하나, **보유기간 가중 age와 최대 stale 기간에서는 안 A가 앞선다.** 둘은 **비중첩 후보**이며 어느 쪽도 상대를 지배하지 않는다. 안 C의 실무 비용은 두 가지 — DART 수집은 동일하게 필요하고, **#24(8/19) 라이브 앵커가 없어 라이브 검증이 11월로 밀린다.**

**실행 무결성.** 코드 대조로 확인한 항목 중 **TTM 연도 위치 정렬**(`_make_ttm`이 리스트 위치를 연속 연도로 가정 — 중간 연도 결측 시 조용히 틀림)이 가장 위험하다. 이것과 거래비용 SSOT 불일치, TTM 리팩터링은 **인컴번트 수치를 바꾸므로 SPEC_13 밖 선행 PR**(§0-A)로 분리해 불변식 2를 지킨다. 캘린더 주입도 날짜 리스트에서 **`RebalancePoint`**(report_type 명시 탑재)로 바꿔 `_report_type()`의 월 추론을 제거한다.

TTM을 판정 기준으로 삼자는 방향은 두 안 모두에서 정확하고 사실상 필수다(§4-4). **G5 실패의 해법으로는 어느 안도 기대해서는 안 된다**(§1-1).

**확정 사항은 §10 표에 집약**(사전등록). 남은 것은 실행 파라미터(TC-PRE 요율·fixture fallback·원문 임계치·공통기간 날짜)뿐이며 Q-A/Q-B 시점에 채워진다.

**다음 순서: P0 선행 부채(DEBT-4→1→2→3, §0-A) → #24 라이브 실행·기록 → Q-A 착수 승인 → Q-B에서 공통기간 동결 → 본 실행(§3 로드맵).** 안 A·안 C를 함께 사전등록 후보로 검정하며, 둘 다 통과해도 자동 선택하지 않고 라이브 포워드로 구분한다.
