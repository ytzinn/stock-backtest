### 1-1. 구간 집합 — **G1과 동일한 n=18 절단**

세 게이트가 **같은 대상**을 서술해야 한다. G1(`e2c2b8d`)이 n=18이므로 G5·G2도 n=18이다.

- **판정**: n=18 절단 집합
- **진단 병기**: 전 완결 구간본(n=20). **판정에 쓰지 않는다.**
  두 값이 다르다고 유리한 쪽을 고르지 않는다.

`[Claude 의견]` 근거: G5(일별 MDD)는 NAV 연속성을 요구하고, G1의 n=18은 복리 연쇄
연속성 때문에 만들어진 집합이다. 두 제약이 같은 성질이라 집합도 같아야 한다.

`[검증된 사실]` **집합은 SSOT 재적용으로 산출했다** — 숫자를 옮겨 적지 않았다.
경로: `scripts/analysis/coverage_slice.{load_rule_coverage, selected_anchors, contiguous_tail}`
+ `scripts/analysis/period_truncation.load_f_periods(root=experiments/_baselines/shadow_20260819)`.

```
완결 구간 (n_stocks>0, next_date 가 앵커)        : 20
임계 탈락 (tau=50%, 규칙 {R1,R2,R5,R6})          : 2016-08-18   (R5·R6 판정가능 0%)
연속화로 추가 상실                                : 2016-04-05
채택 구간                                        : n=18,  2017-04-05 ~ 2026-04-03
```

### 1-2. tape은 **전 구간**으로 생성하고, 절단은 **판정 단계**에서 한다

tape을 18구간으로 잘라 만들면 그 밖의 구간은 **영구히 대조 불가**가 된다.
SPEC_15의 패널은 T=19(2016-04-05 포함)라 L-1a 대조에 그 구간이 필요하다.

- **생성**: 전 구간 (`export_portfolios` 기본 범위 2016-04-05 ~ 2026-04-03)
- **절단**: `run_daily_nav` 결과 슬라이싱 / G2 산출 단계

### 1-3. `period_set` 필드 신설

모든 게이트 산출물 JSON에 아래를 넣는다. `BASELINES.json` 스키마 가드와 같은 성격이다.

```json
"period_set": {
  "n": 18,
  "dates": ["2017-04-05", ...],
  "sha256": "<정렬된 날짜 목록을 LF 로 join 한 문자열의 sha256>",
  "source": "e2c2b8d 절단 집합"
}
```

**`[검증된 사실]` 이 세션이 쓰는 `period_set.sha256`** (산출 전 확정):

```
n      = 18
sha256 = d318d475e89c438dce62873a6c38d1b422c2d042c52cf99eadccb7797495d383
dates  = 2017-04-05 2017-08-18 2018-04-04 2018-08-20 2019-04-03 2019-08-20
         2020-04-03 2020-08-20 2021-04-05 2021-08-19 2022-04-05 2022-08-18
         2023-04-05 2023-08-18 2024-04-03 2024-08-20 2025-04-03 2025-08-20
해시 규약 = sha256("\n".join(sorted(dates)))   # 종료일(next_date)은 포함하지 않는다
```

`[Claude 의견]` 이 필드가 없어서 2026-08-12 오귀속(n=20 tape을 n=13 운영에 사용)과
08-24 세대 혼입이 조용히 통과했다. 필드가 있으면 이후 어떤 비교든 자동 대조된다.

### 1-5. `[산출 전 선언]` G2 벤치마크의 알려진 불일치 — **이 세션에서 고치지 않는다**

`[검증된 사실]` 사전등록 G2의 벤치마크 `U_pbr_path_ew` 는 모멘텀이 **MA 20/60** 이고
채택안은 **MA200** 이다. 즉 G2는 채택안을 **다른 유니버스의 동일가중**과 견준다.
이 불일치는 SPEC_10 §「미해결」에 이미 기록돼 있고 `dashboard/claims.KNOWN` 에 등록돼 있다.

**고치지 않는 이유**: 벤치마크 교체(`U_pbr_ma200_ew` 신설)는 **사전등록 게이트 정의의 변경**이며
별도 사용자 결정 사항이다. 이 세션의 임무는 **같은 정의를 정정된 데이터로 다시 재는 것**이다.

> **그러므로 이 세션의 G2 결과는 "채택안이 MA200 유니버스의 동일가중을 이겼는가"를
> 말하지 않는다.** 그 질문에 답하려면 별도 태그가 필요하다. 판정 문구에 이 한계를 병기한다.
